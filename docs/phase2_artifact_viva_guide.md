# Phase 2 Artifact and Viva Guide

Use this guide to explain what each project artifact does, what evidence it provides, and what it does **not** prove. The Phase 1 model and Phase 2 model are different: Phase 1 predicts same-day daily `Traffic Volume`; Phase 2 predicts a SUMO lane's queue length 60 seconds into the future, in metres.

## One-minute project explanation

The project builds a Bengaluru road-network simulation in SUMO, creates controlled traffic scenarios, records lane-level queue observations, and labels each observation with the queue measured 60 seconds later. A Metaflow workflow trains and evaluates a queue model against a persistence baseline using separate simulation seeds. A FastAPI service exposes the selected model, and Docker packages that service. The project also defines CI and a Render deployment path. Local training, tests, API, Docker, and the pushed branch's GitHub CI have evidence; public hosting has not been verified. Simulation results are not measurements of live Bengaluru traffic.

## Metrics to explain carefully

- **MAE** is the average absolute prediction error. For this queue model the unit is metres.
- **RMSE** penalizes larger errors more than MAE. It is also in metres.
- **R²** compares the model with predicting the test-set mean; it is not a percentage accuracy score.
- The queue test set contains many zero queues. The all-row metrics and the positive-queue subset answer different questions, so show both.
- On all held-out rows the model beats persistence (MAE 0.0550 vs 0.0694 m). On the 2,753 rows with a positive future queue, persistence has the lower MAE (1.902 vs 2.200 m) while the model has the lower RMSE (3.237 vs 3.438 m). On the 3,357 rows with a queue now or 60 s later, the model is better (MAE 1.832 vs 2.318 m). Quote these together; do not claim a positive-subset MAE improvement. This is evidence about queue prediction for these simulations; it is not evidence that the predictive signal controller beats fixed-time control.
- Controller outcome metrics and queue prediction metrics are different. A model can predict queues reasonably while a policy using it still fails to improve travel or waiting outcomes.

## Suggested demonstration sequence

1. Open `docs/phase2_handoff_summary.md` and explain the target distinction and current limitations.
2. Show the corridor in SUMO-GUI with the actual `demo.sumocfg`; say clearly that this is a simulated corridor and assumed demand, not live city traffic.
3. Show the flow file and the recorded Metaflow run/report. Explain run-based data splits and the persistence comparison.
4. Show the metric table in `reports/phase2_osm_results.md`, including positive-queue metrics and the controller caveat.
5. Show the API smoke responses, then the Dockerfile and local container check.
6. Show `.github/workflows/phase2-ci.yml` and `render.yaml`, while accurately saying that GitHub Actions and hosted deployment still need actual runs/configuration.

If asked whether the project is fully deployed, answer: **“The Phase 2 model workflow, tests, local API checks, and GitHub CI on `main` passed. A gated CI deploy reached a Render service whose health check returned 200, but we have not verified a hosted prediction. DVC remote availability has not been checked.”**
